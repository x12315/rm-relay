# 为什么 RM 队伍需要共同维护开发基础设施

RM 队伍看起来像一个小型研发团队，却很少具备企业中的专职平台、运维和底层工具团队。
成员水平不一，服务器和设备有限，人员又以学年和赛季为周期更替。一套依赖少数人维护的
开发环境，常在核心成员离队后变成无人敢升级的黑箱。

## 为什么共享基础设施

控制、视觉和规划算法需要不断穷究原理与问题本质。它们会随赛季、机器人和队伍方案继续
深入，很难形成长期稳定的通用框架；过早统一反而可能限制研究。

开发基础设施的生长方向不同。编译器、构建系统、容器、烧录、调试和验证方法建立在相对
稳定的工程事实之上，可以从底层逐步补齐。新增板卡或平台不必推翻已有入口，来自不同队伍
的验证也能累积为共同资产。单支队伍难以覆盖所有主机、板卡和调试器，多支队伍却可以各自
验证手里的真实组合。因此，基础设施更适合跨队伍维护。

RM Relay 共享的是开发环境和工程方法，不统一各队的机器人应用，也不要求公开有竞争性的
算法、参数或赛场策略。

## 已有工具与项目工作

GCC、Clang、CMake、OpenOCD、GDB 和 Docker 已经开源，但这些工具不会自动形成适合
新人的稳定组合。用户仍需处理版本、宿主平台、设备权限、网络和工程边界。

本项目选择成熟上游，固定经过验证的组合，并提供镜像、模板、配置和可执行验证。自研代码
只补足必要的连接处。大体积镜像和构建流量优先使用国内基础设施，少量源码仍连接原始上游；
本地 Docker 路径始终保留，不让项目只能依赖某台服务器。

## 我们希望谁来参与

我们尤其希望有余力的战队参与：由具备软件工程经验的主力队员提供真实使用和平台验证，
也欢迎高年级或已经毕业的 RM 队员，把曾经为开发环境、工具链或交接发过的愁变成下一届
可以直接使用的成果。

贡献不必很大。一份板卡配置、一次真实平台验证，或把队内口口相传的操作写清楚，都能减少
其他队伍的重复劳动。当前优先级见[路线图](../../ROADMAP.md)，提交方式见
[贡献指南](../../CONTRIBUTING.md)。
